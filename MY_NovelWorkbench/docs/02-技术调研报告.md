## 0. 执行摘要

**一句话结论**：需求中的全部核心概念（ComfyUI 式可进入子图蓝图画布、Obsidian 式双链图谱、链路驱动的 AI 上下文组装、PyCharm 式布局）在开源世界均有成熟先例或可组合方案，无一项需要从零发明；最大的技术风险点是「跨子图连线的数据模型」，建议以 1-2 周 PoC 先行验证。

**推荐技术栈（待讨论确认）**：

| 层 | 推荐 | 理由摘要 |
|---|---|---|
| 桌面框架 | **Electron** | 中文 IME 稳定性 > 包体积；VS Code/Obsidian 同路线 |
| 前端框架 | **React 18 + TypeScript** | React Flow 生态绑定 React，社区最大 |
| 蓝图画布 | **React Flow (@xyflow/react) v12** | MIT；子图/语义连线/小地图/黑色网格全命中 |
| 全局图谱 | **AntV G6 5.x**（Graphin 3 React 封装） | MIT、中文文档、力导向布局内置 |
| 正文编辑器 | **Tiptap**（或 CodeMirror 6） | 支持 [[双链]] 标记与流式插入 |
| 状态管理 | **zustand** | React Flow 官方推荐搭配 |
| 数据存储 | **纯文件真相源 + SQLite 索引缓存** | Markdown+JSON 对 git 友好；索引可重建 |
| AI 接入 | **自写 OpenAI 兼容 Provider 层** | 一套 baseURL+key+model 覆盖 90% 厂商 |

### 1.1 国际产品：上下文管理的三种成熟范式

| 产品 | 定价 | 核心机制 | 对本项目的启示 |
|---|---|---|---|
| **NovelAI** (Lorebook) | $10-25/月 | **关键词触发 + token 预算**：条目绑定关键词，命中最近文本扫描窗口即激活；按 Insertion Order 排序、每条目独立 Token Budget，条目间竞争上下文空间；提供 Context Viewer 查看最终组装结果 | 优先级 + 预算双参数的标杆实现；**Context Viewer 式上下文预览面板值得直接做**（让作者看到蓝图链路实际组装出的 prompt） |

### 1.3 学术前沿

- **StoryNode（CHI 2025）**《Toward Personalizable AI Node Graph Creative Writing》：FigJam 插件，故事事件组织为可自由编辑节点图 + 挂载多种生成式 AI——「节点画布 × AI 创作」最直接的先行研究，立项论证的关键引用
- **InfraNodus**：知识图谱分析型思路——图谱视图除导航外可做**缺口提示**（哪些设定节点孤立、哪些伏笔未回收），对应我们的「伏笔」标签闭环
- **DHO（NAACL 2025）**：动态层级大纲 + 记忆增强维持 10 万字级一致性——为「上级蓝图以摘要注入」提供学术背书

**关键判断**：目前**没有任何主流商业产品提供 ComfyUI 式自由节点画布创作界面**（最接近的是 StoryNode 学术插件与只读图谱的墨狐）。节点/图谱交互是未商业验证的蓝海——既有差异化空间，也有「非写手习惯」的采用风险。对策：**节点画布做组织/规划层，正文编辑保留传统编辑器**（PyCharm 布局方向正确）。

|---|---|---|---|---|---|

| tldraw | **source-available，商用需付费 license key** | 活跃 | - | - | **排除**（授权风险） |

**白板类（tldraw/Excalidraw）整体不适合做节点蓝图编辑器**：自由绘制为核心，节点-端口-连线是二等公民。

**性能预期**：小说创作单画布节点量（几十~几百）远低于 n8n/ComfyUI 规模，React Flow 的 SVG 渲染 + `onlyRenderVisibleElements` 视口虚拟化 + 节点 memo + zustand 选择器完全够用；无需 WebGL。

## 3. 三大核心技术问题专项结论（补盲阶段）

### 3.1 子图嵌套：React Flow 的「进入式蓝图」如何实现

**结论：可行，但必须自建数据层，且这是全项目第一技术风险点。**

- React Flow 官方 subflow（`parentId + extent:'parent'`）是**画布内视觉分组**，不是双击进入的独立子图——所有节点同坐标系，不能实现「进入」体验；且已知一批嵌套场景边交互 bug（#5203/#2798/#4495 等）
- **路由式进入是社区验证的成熟模式**：`onNodeDoubleClick` 是一等公民 API → 前端路由切换渲染新的 `<ReactFlow>` 实例加载子图；有实战先例代码与已知坑记录（条件面板卸载后双击失效等）
- ComfyUI/LiteGraph（及 Gaffer 的 Box 节点、Material Maker、Graphite）证明「双击进入+面包屑+递归嵌套+边界 IO 映射」是节点编辑器领域反复验证的设计范式
- **核心风险不在交互而在数据模型**：跨子图连线、父子状态同步、递归嵌套均无库级支持
- **推荐数据结构**：一张全局节点/边表 + 每个蓝图一个视图；边引用 node id 而非归属图；上级链路遍历 = 沿 parent 图指针回溯（与文件夹路径同构）
- **行动项：1-2 周 PoC**（React Flow + 路由式下钻 + 跨图边数据层），验证后再冻结画布库选型

### 3.2 全局图谱视图与双链索引

- **图谱库选型：AntV G6 5.x**（MIT、活跃、中文文档、力导向/树/辐射布局内置、深色主题定制）；React 集成用 Graphin 3 或 @antv/g6-extension-react。react-force-graph 仅在要 3D 漫游时考虑；Cytoscape.js 偏分析型不推荐
- **数据协同**：图谱视图不复用画布坐标，而是读同一份节点/边 JSON 的「逻辑图」投影——蓝图节点（嵌套子图作为超节点）、语义连线与 [[双链]] 统一为 edge，带 `type` 字段（wikilink / 箭头 / 虚线 / 父子）；按标签（设定/伏笔/大纲/世界观）着色与过滤
- **存储语法冻结建议**：正文用 [[wikilink]]；**frontmatter 只放标签/元数据、绝不放链接**（两个方向都有索引坑）；结构性关系放蓝图 JSON 的 edges 字段
- **索引层**：SQLite 缓存 + 文件监听增量更新（chokidar），参考 MarkdownDB 的三表结构扩展：`nodes(id,path,type,tags,mtime,hash)` / `edges(source_id,target_id,type)`；mtime/hash 变更才重解析；提供「重建索引」兜底命令（SilverBullet 的反例：>5k 文件全量重建明显卡顿）

### 3.3 AI 上下文组装策略（核心差异化能力的设计草案）

**业界三种成熟范式**（参数设计直接复用）：NovelAI 的 Insertion Order + Token Budget；SillyTavern 的 Priority（超预算先丢低优先级）+ Scan Depth + Recursion 上限；NovelCrafter 的 mention 触发 + 手动挂载 + 关系级联。我们的「结构化链路驱动」是**第四种触发器**（图遍历替代关键词扫描），有 GraphRAG 行业共识背书（图遍历保证事实链、向量/关键词做模糊兜底）。

**推荐组装规则（草案）**：

1. **优先级三层**：① 当前节点 + 直接前后链接节点（全文）＞ ② 上级蓝图链各级的「摘要卡片」（50-100 字/蓝图，而非全文）＞ ③ 深度 ≥2 的链接节点按边语义加权（设定/伏笔边权重高于弱关联边）
2. **token 预算分层**：如总预算 60/25/15% 分配给三层
3. **深度截断**：链路展开默认 2-3 层（SillyTavern 递归不加约束会爆的教训）
4. **关键词兜底**：链路遍历未填满预算时，对当前草稿文本做节点标签/别名关键词匹配补齐——竞品的主路径降级为我们的兜底路径
5. **两层摘要压缩**：蓝图节点维护摘要卡（子图全文仅进入时加载）+ 章节递归摘要做「最近剧情」——使注入规模与小说总字数**近似解耦**，这是长篇不崩的结构保证
6. **节点粒度约束**：以「一张摘要卡能概括」为上限（约 500-1000 字），超限拆子节点——token 预算可按节点数粗粒度控制

**量化可行性**：中文约 0.6-0.7 token/字；20 节点 × 500 字链路 ≈ 6-7k token，仅占 128k 窗口 5%；即使 100 节点（≈30k token）+ 近期 1 万字正文（≈7k token）仍远未超限。**结论：10 万字/上百节点规模完全可行，无需早期过度优化；真正风险是无约束图遍历，故「深度截断+预算+优先级丢弃」三件套第一天就要进设计。**

## 4. 技术栈与架构选型

### 4.1 桌面框架：Electron（推荐）

- 本项目是**重文本输入的中文用户工具**，IME 稳定性优先级高于包体积——VS Code/Obsidian 均为此留在 Electron（自带完整 Chromium，跨平台行为一致）
- Tauri v2（包 3.2MB、内存低 58-75%）依赖系统 WebView，IME/渲染行为随 WebView 版本波动，已有开发者回迁；Windows WebView2 体验尚可但一致性仍是最大风险
- 结论：**Electron 低风险起步；未来极在意体积再评估 Tauri**

### 4.2 数据存储：混合方案（推荐）

- **真相源 = 纯文件**：正文 Markdown + frontmatter（标签/别名）+ [[wikilink]] 正文双链；蓝图 JSON（参考 JSON Canvas 扩展 + ComfyUI 双格式思想：同时存 UI 布局与执行图）
- **索引缓存 = SQLite**（better-sqlite3）：链接/标签/资源库元数据，可从文件随时重建——Markdown 可移植性与图查询性能的折中（Glyph for Mac、MarkdownDB 同构先例）
- git 友好、用户可用任意编辑器打开、防弃坑（Logseq 教训）

### 4.3 AI 多厂商接入：自写 Provider 层（推荐）

- **OpenAI 兼容协议已是事实标准**：DeepSeek、智谱 GLM、Moonshot、阿里百炼、Ollama 等全部兼容——自写几百行 Provider 配置层（baseURL + apiKey + model 列表映射到 openai SDK）覆盖 90% 厂商
- LiteLLM（100+ provider）作可选依赖；one-api/new-api 网关作为用户自选外部方案，**不内置**（个人桌面应用跑网关进程过重）
- **流式输出**：fetch + ReadableStream 解析 SSE（不用 EventSource——需自定义 Header）；编辑器侧节流/批量插入避免逐 token 重排
- 多模型路由参考 AI_NovelGenerator：不同任务（大纲/正文/润色）绑定不同模型预设

### 4.4 UI 骨架

- PyCharm 式多面板：CSS Grid/Flexbox + 可拖动 resizer 自实现（或 Allotment 库）
- 深色主题：给定色板直接落 CSS 变量（#191A1C/#1E1F22/#26282B/#545557），与国际产品审美一致，无采用风险
- 正文编辑器内核：**Tiptap**（需 [[双链]] 悬浮预览与流式插入）或 CodeMirror 6（轻量性能向）

## 5. 核验纠错与风险提示

**核验纠错（10 条论断，8 证实 2 纠错）**：

| 1 | 应用形态 | **Electron 桌面应用**（本地优先契合创作数据私有） | 先做 Web 版快速迭代（但本地文件访问受限） |
